# 後續功能規劃

## 情境修正

原本按「辦公室團購」設計，實際情境是**一群人出去玩，到店後各自用自己的手機掃／開連結點餐，最後一起結帳**。

差異在哪裡：

| | 團購（原本假設） | 出去玩（實際） |
|---|---|---|
| 大家在不在同一處 | 分散在辦公室 | 同一桌 |
| 為什麼要記名字 | 誰要吃什麼 | **結帳時算錢** |
| 截止時間 | 重要（要合併叫餐） | 幾乎用不到 |
| 誰去下單 | 開團者統一叫 | 現場直接跟店家點 |
| 核心產出 | 給店家的叫餐單 | **誰該付多少、誰付過了** |

架構本身不用改 —— 各自用自己的手機，「一個裝置一筆訂單」的憑證模型仍然成立。要調整的是**重心**：從「叫餐」轉向「結帳」。

## 已完成

- 名字 autocomplete（本機記錄，換一攤不用重打，並排除本攤已用過的名字）

## 建議順序

### 第一優先：結帳功能

這是情境改變後真正缺的東西。目前彙總只算得出「每個人多少錢」，但實際結帳還需要：

**1. 標記誰付過了**

`orders` 加 `paid_at timestamptz`。結帳頁每個人一個勾選框，點一下記錄已付。收錢的人最需要的是「還差誰沒給」，不是總金額。

```
小明   $320  ✓ 已付
小華   $280  ○ 未付
小美   $450  ○ 未付
────────────────
已收 $320 ／ 還差 $730
```

**2. 服務費與均分項目**

出去玩常有「一鍋湯大家分」「服務費 10%」這種不屬於單一個人的金額。

`group_orders` 加 `service_charge_percent int` 和 `shared_items` 的概念。均分金額除不盡時要有明確規則（建議餘數由發起人吸收，並在介面標示），否則會出現總和對不起來的窘境。

**3. 付款方式提示**

發起人可以填一段收款資訊（LINE Pay 連結、銀行末五碼），顯示在結帳頁。純文字欄位即可，不做金流串接。

### 第二優先：現場點餐的體驗

**4. 用語調整**

「團」→「這攤」、「開團」→「開始點餐」、「關團」→「結束點餐」。目前介面用語仍是團購脈絡，現場使用會覺得怪。

**5. 截止時間改為選填且預設關閉**

現在預設今天 11:30，出去玩的情境完全用不到，反而會誤擋下單。

**6. 即時看到別人點了什麼**

大家坐在同一桌，會想知道「有人點過那道了嗎」。目前要手動切 tab 重新整理。加一個輕量輪詢（10 秒）即可，不需要 WebSocket。

### 第三優先：便利性

**7. 常用品項建議**

從歷史 `order_items` 統計這家店最常被點的品項，排在菜單前面。

**8. 複製上一攤**

同一群人常去同一家店，一鍵沿用上次的店家與成員名單。

**9. 分帳截圖**

結帳頁產生一張可存圖或複製的純文字明細，直接貼群組。目前已有複製文字，可再加上每人金額版本。

## 明確不做

- 金流串接（掃碼付款、線上刷卡）—— 出去玩就是現場給現金或轉帳，串金流的成本遠大於效益
- 帳號系統 —— 零阻力是這個工具的價值來源
- 廚房端／出單機 —— 這是店家的系統，不是我們的範圍
